# 真实场景应用展厅优化审查

审查日期：2026-08-04

审查对象：`/applications.html`，桌面 1280 × 720，移动 390 × 844。

## 证据步骤

1. `01-desktop-rural.png`：默认乡村四季首屏。场景、价值面板、过程阶段、场景控制和应用目录同时出现，功能完整，但首个行动不够明确。
2. `02-park-twin.png`：园区孪生总览。建筑、道路、绿化、摄像头路线都能被看见，场景辨识度良好；右侧面板和左侧大标题会压缩可观察的 3D 区域。
3. `03-mobile-park.png`：手机端园区孪生控制状态。没有横向溢出，控制面板可用，但用户需要滚动才能在“场景 / 说明 / 控制 / 目录”之间来回切换。
4. `04-mobile-park-top.png`：手机端首屏。标题和应用价值优先级清楚，但过程和图层控件在首屏下方，第一次体验不容易发现它们。

## 总体判断

Three.js 3D 能力已经足够展示，当前优先级应从“增加更多效果”转向“降低理解成本”。页面需要从展示海报升级为一条明确的体验路径：选择案例 → 看过程 → 操作空间 → 对应产品用途。

## 优先级建议

### P0：先解决理解问题

- 在首屏增加一条 4 步引导：`选择场景 → 观察构建 → 拖动 3D → 对应业务用途`，并提供一个明确的“开始体验”按钮。
- 把当前阶段的 `title`、`copy` 和“这一阶段对产品有什么意义”放进过程面板。现在阶段按钮只有短标签，旁边主要显示 `INPUT` 和 `GPU OPERATION`，用户能看到技术词，却不容易理解过程。
- 为园区增加“业务视图”入口：`物业巡检`、`空间导览`、`园区展示`。同一套 3D 能力用不同任务驱动，产品意义会比单纯切换图层更清楚。
- 把“程序化演示 / 尚未接入真实数据”做成场景内的状态标签，避免用户误以为已经连接真实摄像头、GIS 或物业数据。

### P1：提升空间可读性和操作效率

- 增加对象选中态：点击建筑、道路或摄像头后显示名称、用途、状态和所在图层；目前只能整体切换，缺少“我点到的是什么”的反馈。
- 增加园区图例、北向、比例尺和入口/中庭/东侧通道标签，让它从“漂亮的程序化场景”更接近“可讨论的空间模型”。
- 将“摄像头视角”明确标为“预设视角”，并显示 `CAM-01 / 园区主门` 等信息，避免被理解为真实视频流。
- 桌面端提供“讲解视图 / 纯 3D 视图”两个明确模式；当前大标题、右侧面板和左下控件会压住一部分场景。
- 手机端将过程说明、图层控制和天气控制改为可折叠抽屉或底部固定工具栏，减少长页面滚动和上下寻找。
- 应用目录增加“左右滑动查看更多”的提示，并在移动端保留当前案例名称，避免用户只看到编号和很小的标签。

### P1：完善无障碍与反馈

- 为季节、天气、园区图层和镜头按钮补充 `aria-pressed` 或等价的选中状态；阶段按钮已有部分状态语义，但其他控件还不一致。
- 让画布可通过键盘获得焦点，并提供“拖动旋转 / 滚轮缩放 / 方向键选择阶段”的可见说明；目前主要依赖鼠标、触摸和隐含的底部提示。
- 提高小号英文标签和低对比度说明文字的字号与对比度；当前截图中 `INPUT`、`GPU OPERATION`、运行指标和底部状态文字偏小。
- 把阶段变化、天气变化和应用切换用明确的 `aria-live` 状态播报，避免屏幕阅读器用户只看到按钮变化但不知道场景发生了什么。

### P2：性能和真实数据接入准备

- 当前启动时同时创建乡村世界和园区世界，只是把其中一个隐藏；后续应按案例懒加载，减少首屏内存和初始化时间。
- 建筑窗户、树木和重复标记可以逐步改为 `InstancedMesh`，再增加低质量 / 中质量 / 高质量三档，给移动端留出余量。
- 为真实园区接入预留统一数据契约：建筑 GLB / glTF、道路 GIS、摄像头点位、楼层信息、巡检状态和时间戳，不要让后续数据直接绑死在场景代码中。

## 下一轮最值得做的 3 件事

1. 先补“阶段标题 + 过程解释 + 产品意义”面板；
2. 增加建筑/摄像头点击详情和园区图例；
3. 把手机端控制改成底部抽屉，并增加清晰的 3D 手势引导。

这些调整不会改变现有 Three.js 场景底座，但会明显提升用户对“这个 skill 能做什么、为什么对产品有意义、下一步如何继续”的理解。
