## 这套文档解决什么问题

网页负责让人快速理解项目全貌；这里的 Markdown 文档负责把讨论变成可以执行、检查和持续修改的设计依据。

所有后续开发都应当能够回答三个问题：

1. 它服务于哪一种玩家体验？
2. 它改变了哪些世界状态，又通过什么方式呈现？
3. 我们用什么可观察证据判断它已经成立？

如果一个功能只能回答“看起来不错”或“其他生存游戏也有”，它还没有进入开发阶段。

## 现有资料如何处理

项目根目录中的 `VISION.md`、`WORLD_GEOGRAPHY.md`、`VERTICAL_SLICE.md`、`ASSET_PLAN.md` 等文件是此前原型阶段形成的资料，暂时保留作为历史依据。

从本轮开始：

- 本目录是正式设计入口；
- 网页与本目录使用相同术语；
- 原型实现细节不自动成为正式设计；
- 如果文档与当前运行原型不同，以文档标注的“目标”和“当前边界”为准；
- 重大决定必须记录原因、验证方式和重新评估条件。

## 统一术语

| 术语 | 含义 |
| --- | --- |
| 世界运行层 | 保存状态并执行规则的内部世界，不负责最终画面 |
| 世界表现层 | 把内部状态转换成模型、材质、光照、动画、声音与界面 |
| 玩家证据 | 玩家能够观察到、并据此判断世界状态的线索 |
| 选择性真实 | 只模拟影响体验和决策的现实规律，其余使用可信近似 |
| 技术切片 | 用于验证地形、人物、物理、海水和画质基础的最小区域 |
| 垂直切片 | 在小范围内包含接近最终质量的完整游玩闭环 |
| 阶段门 | 未满足明确验收条件之前，不进入下一阶段的开发控制点 |
| 可信陌生 | 环境暂时难以读懂，但所有重要现象具有真实原因和可观察线索 |
| 探索语法 | 线索、假设、准备、验证、后果与持久知识构成的发现过程 |
| 受控生成 | 固定可信地理骨架，只在世界条件约束下改变天气、生物、资源和事件 |
| 独自上岸 | 主角抵达时身边没有其他人，但故事尚未确认其为唯一幸存者 |
| 地区客货船 | 在偏远岛屿间同时运送乘客和物资的中小型船只，用于替代不可信的大型邮轮失踪设定 |

## 文档维护规则

1. 每份文档顶部标注状态和最近一次重大修订。
2. 新系统必须同时定义状态、规则、表现、依赖与验收证据。
3. 修改一个系统时，检查它对相邻系统和存档的影响。
4. 概念图、原型截图和运行截图必须明确标注，不能混用。
5. 未决定的内容写成“待决策”，不能用模糊措辞假装已经确定。
6. 已经被验证推翻的方案保留简短原因，避免以后重复走同一条路。
