# 06 · 技术架构

> 状态：基础版 R1  
> 目的：给出不依赖特定引擎的世界架构，并定义后续引擎选择方法。

## 架构目标

技术必须支持三件事：

1. 世界在玩家不操作时也能持续变化；
2. 系统状态和最终表现可以分别修改、测试和替换；
3. 小区域验证成功后可以逐步扩展，而不是重写所有内容。

## 总体分层

```text
输入层
  玩家操作 / 设备 / 辅助功能
        ↓
行动层
  移动 / 互动 / 使用工具 / 建造
        ↓
世界运行层
  地理 / 气候 / 物理 / 生态 / 人物 / 资源 / 事件
        ↓
统一世界状态与事件
        ↓
世界表现层
  场景 / 材质 / 光照 / 动画 / VFX / 声音 / UI
        ↓
保存、回放、自动测试与性能记录
```

## 世界运行层模块

### World Clock

提供游戏时间、昼夜、暂停、时间倍率和固定更新步长。系统不各自读取真实系统时间。

### Region Model

保存区域 ID、边界、高度、表面、气候暴露、生态类型、资源和事件标签。地理装饰不直接兼任所有玩法数据。

### Environment State

统一保存太阳、温度、湿度、气压、风、云、雨、潮位和海况，向其他系统发布只读事实。

### Character State

保存身体、装备、知识、当前位置和动作状态。动作系统提出消耗，人物系统计算结果。

### Ecology State

管理近处个体与远处种群，不要求整座岛所有动物每帧运行完整行为树。

### Resource and Construction State

管理世界资源实例、背包、工具、加工、建筑和永久场景改变。

### Event State

读取条件、记录触发历史并发布事件结果，不直接控制最终画面。

## 表现层模块

- Terrain View：地形网格、材质混合、细节层级；
- Ocean View：海面、岸浪、白沫、浅水和反射；
- Atmosphere View：天空、云、雾、太阳、雨和光照；
- Vegetation View：植被实例、风动、距离细节和湿润状态；
- Character View：模型、骨骼、动作、装备挂点和材质状态；
- Creature View：模型、动作、群体呈现和可见反馈；
- Audio View：环境层、空间声、人物与行动反馈；
- Interface View：状态确认、背包、设置和辅助信息。

每个表现模块读取世界状态，不自行定义游戏事实。

## 数据与代码分离

下列内容优先数据化：

- 区域范围、地表和标签；
- 物种栖息地、时段和天气修正；
- 资源属性、来源和配方；
- 建筑功能和遮蔽参数；
- 天气状态与过渡条件；
- 事件触发条件和结果；
- 动作消耗和身体状态参数。

这样设计人员可以调整内容，而不需要修改核心运行代码。

## 系统通信

采用“事实输出”和“结果自算”的原则：

- 天气发布降雨强度；
- 火堆读取降雨、遮蔽和木材湿度，自己计算强度；
- 人物读取温度、风、雨和动作，自己计算体温；
- 表现层读取火堆强度和人物体温，生成视觉与动作反馈。

避免天气系统直接修改火堆、人物、动物和音效，这会让系统关系难以测试和扩展。

## 物理边界

视觉地形、玩法碰撞和导航数据可以来源相同，但要允许独立优化：

- 高精度视觉网格不直接等于碰撞网格；
- 碰撞保留坡度、岩石和岸线等玩法轮廓；
- 导航记录可通行性、水深和区域成本；
- 交互使用明确范围、视线和目标层；
- 关键移动使用固定时间步，减少帧率变化带来的差异。

## 保存与迁移

存档保存系统状态，而不是保存渲染对象：

- 游戏时间和天气；
- 人物位置、身体、背包和知识；
- 已采集资源和恢复时间；
- 动物或区域的必要持久状态；
- 建筑、工具和营地状态；
- 已触发事件和发现地点；
- 存档版本号。

每次结构变化提供从旧版本到新版本的迁移；加载失败不能静默丢失进度。

## 测试入口

每个跨系统场景需要固定复现条件，例如：

- 暴雨前 3 分钟；
- 暴露火堆与棚下火堆对比；
- 低潮潮池；
- 人物潮湿且体温下降；
- 鱼群和海鸟联动；
- 资源采集前后；
- 保存后重新加载。

固定入口不是作弊功能，而是让复杂世界能够回归测试的必要工具。

## 引擎角色分工

当前不把最终生产引擎视为无条件结论，但不再要求两条路线重复建设同等写实场景。现有 Three.js 原型保留为设计与系统实验台；Unreal 是写实表现与最终生产的首选候选：

| 维度 | 浏览器 / Three.js 路线 | Unreal 路线 |
| --- | --- | --- |
| 访问 | 链接即开，传播和研究方便 | 需要安装或分发客户端 |
| 写实基础 | 需要自行组合地形、海水、物理和光照方案 | 成熟的地形、水体、光照、植被和资产工具 |
| 工程自由 | 代码与网页界面结合灵活 | 引擎工作流和编辑器能力强 |
| 性能范围 | 受浏览器、显存和移动设备约束明显 | 更适合高规格桌面和主机目标 |
| 团队门槛 | Web 技术已有基础 | 需要学习编辑器、蓝图/C++和资产管线 |
| 适合验证 | 系统研究、快速分享、交互原型 | 最终写实画面和大型三维生产 |

## 引擎决策门

Unreal 基准使用与现有原型一致的参考区域、人物尺度、天气状态和镜头要求，并根据真实运行证据评估：

- 达到目标画面的时间；
- 地形与碰撞制作效率；
- 海水和天气质量；
- 人物动画与交互难度；
- 目标设备性能；
- 资产兼容、授权和后期扩展；
- 学习成本与长期维护风险。

基准完成前，不为任何路线大量购买资产或扩展完整地图。详细执行和停止条件见 [09_PRODUCTION_DECISION_AND_BLOCKERS.md](09_PRODUCTION_DECISION_AND_BLOCKERS.md) 与 [10_UNREAL_BENCHMARK_PLAN.md](10_UNREAL_BENCHMARK_PLAN.md)。
