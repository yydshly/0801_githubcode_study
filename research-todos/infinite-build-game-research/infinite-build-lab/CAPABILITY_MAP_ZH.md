# The Infinite Build 中文能力地图

## 一句话定位

它是一套让 Codex 在明确授权和边界内，长期承担游戏技术与玩法负责人角色的项目工作流；它不是新的模型、游戏引擎或可下载安装到代码里的库。

## 六项核心能力

| 能力 | 输入 | Codex负责的工作 | 可检查的输出 |
| --- | --- | --- | --- |
| 概念定向 | 游戏想法、玩家幻想、核心动作、气氛、参考和禁区 | 生成几个一致且技术可实现的玩法状态，提出系统方案 | 概念图、系统提案、用户确认 |
| 最小可玩切片 | 已批准的概念方向 | 制作只证明核心体验的 5–10 分钟版本 | 能运行、能操作、有选择与回报的试玩版 |
| 反馈翻译 | 用户的试玩感受 | 找到感受背后最主要的实现问题，只做一个聚焦修改 | 一个有验收条件的检查点 |
| 长期目标 | 当前代码库、历史、路线图、边界与授权 | 保存项目承诺，从最新验证版本继续，不重复从头设计 | 可恢复的项目状态和持续任务 |
| 真实验证 | 当前本地和已部署版本、目标输入与视口 | 实际运行、操作和观察画面，而不只检查代码或单元测试 | 截图、操作结果、测试和回归记录 |
| 发布循环 | 已通过质量门槛的检查点 | 更新版本、提交、推送、部署、线上复查并继续选题 | 可玩的发布版、更新日志和下一个检查点 |

## 关键术语

### Gameplay concept（玩法概念图）

接近实际游戏截图的方向稿，不是只有气氛的宣传插画。它用于约束镜头、比例、UI、资产复杂度和可实现程度。

### Vertical slice（垂直切片）

内容很少但体验相对完整的试玩样品。它要证明核心动作和游戏感觉，不负责容纳完整剧情、大地图、大量角色或长期成长系统。

### Standing goal（长期目标）

跨多次工作继续有效的职责与目标。它记录游戏承诺、允许 Codex自行处理的事项、必须询问人的边界，以及每轮需要执行的验证流程。

### Checkpoint（检查点）

一个范围有限、玩家能感受到、可以独立验证和发布的小版本。例如“让冲刺更有重量感”，而不是“完善所有战斗系统”。

### Companion site（伴随网站）

将最新版试玩、当前工作、下一步计划、版本日志和发布证据放在一起的项目页面。本项目的 `index.html` 就是它的最小原型。

## 人和 Codex 的职责

| 人负责 | Codex负责 |
| --- | --- |
| 游戏承诺与想表达的体验 | 阅读和理解整个现有项目 |
| 审美判断、试玩感受和禁区 | 将感受转成技术与设计改进 |
| 付费、账号、所有权和公开范围 | 编写代码、测试、路线图和更新日志 |
| 是否改变核心玩法 | 在授权范围内提交、部署并验证 |

## 它真正增强了什么

1. **连续性**：下次从最新已验证版本继续，而不是重新猜测项目方向。
2. **聚焦能力**：每次选择一个对玩家影响最大的弱点，限制无关功能扩张。
3. **证据意识**：必须运行真实游戏、使用目标输入并检查最终画面。
4. **项目卫生**：路线图、日志、版本和验证记录由开发循环同步维护。
5. **有边界的自主性**：常规工作不反复请求批准，越过产品或安全边界才暂停。

## 它不能代替什么

- 不能凭空保证游戏一定有趣，人的试玩和审美判断仍然关键。
- 不能把不明确的核心创意自动变成正确产品方向。
- 不能代替付费资产、专业美术、音乐、服务器和平台账号。
- 不能在没有权限时自行公开、花钱、使用密钥或执行不可逆操作。
- 不能只靠单元测试证明手感、画面和设备适配；这些必须真实运行。

## 原网页的完整流程（中文压缩版）

1. **Start**：提供创意，先看可实现的概念状态，再制作最小可玩切片。
2. **Steer**：试玩并描述感受，Codex只修改最重要的不匹配。
3. **Goal**：检查现状后建立长期目标和权限边界。
4. **Companion**：维护可试玩、可查看进度与日志的伴随网站。
5. **Stream**：在同一任务中继续，按检查点循环推进。

## 暂停条件

遇到以下情况应暂停并询问人：改变核心游戏承诺；越过明确禁区；产生费用；新增付费服务或密钥；改变访问权、所有权或公开范围；进行不可逆操作；无法安全测试或验证即将发布的内容。
