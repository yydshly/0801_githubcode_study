# Research 08 · 方法学习与技能沉淀台账

## 研究原则

产品不是最终研究结论，而是用于验证方法的实验装置。每一次开发必须同时交付两条结果：

1. **产品轨**：玩家能看到、操作和验证的版本；
2. **学习轨**：我们理解了哪个步骤、出现了什么失败、哪些做法值得复用。

如果只有产品，没有步骤解释，这次研究不可复用；如果只有总结，没有运行证据，这次研究不成立。

## 每一步必须回答的七个问题

| 字段 | 必须回答的问题 |
| --- | --- |
| 目的 | 这一步究竟要减少哪一种不确定性？ |
| 输入 | 人、案例、代码、资产和约束分别提供了什么？ |
| 动作 | Codex 实际执行了哪些最小动作？ |
| 产物 | 产生了哪些可以检查的文件、页面或游戏状态？ |
| 证据 | 什么运行结果证明这一步成立？ |
| 失败 | 哪些假设、实现或表达没有成立？为什么？ |
| 沉淀 | 下次遇到相似问题，可以复用哪条方法？还缺几次验证？ |

## Stage 01 · 概念定向

### 目的

在编写游戏代码之前，先判断同一游戏是否能够用统一镜头、地形、人物比例和状态变化表达“到达—理解—回报”。减少视觉方向和玩法状态不一致的风险。

### 输入

- 人提供：荒岛求生幻想、现实边界、孤独但不绝望的情绪目标；
- 四案例提供：先概念、后切片的工作顺序，以及风格化浏览器游戏的可实现范围；
- 技术约束：小型 Three.js 切片、简单资产、相同镜头、没有完整生存系统。

### 动作

生成一个三联画，而不是三张独立宣传图；强制人物、海湾、火台、镜头和 HUD 语言保持一致，只改变游戏进程。

### 产物与证据

- `assets/concepts/tidewatch-three-states-v1.png`
- `TIDEWATCH_CONCEPT_V1_REVIEW.md`
- 三个状态能够分别读出到达、收集和点火回报。

### 失败与修正

- 第二状态表达了“取得木材”，但没有清楚表达“读懂潮汐”；
- HUD 暗示了生命、饮水、饥饿和背包，使范围出现膨胀；
- 概念图只能证明视觉状态，不能证明移动、碰撞和潮汐已经可玩。

### 技能候选

`concept-to-playable-state-contract`：把模糊游戏幻想转换为同镜头、同世界、不同进程的状态契约。当前验证 `1 / 2` 个不同样例。

## Stage 02 · 首个可玩切片

### 目的

不追求完整游戏，只验证一个玩家闭环是否成立：读潮 → 选择路线 → 收集木材 → 承担高潮风险 → 点火并获得世界回应。

### 输入

- Adventure：即时行动、目标和回报；
- Online：状态反馈、保存与继续；
- Backroom：环境引导、压力和光照叙事；
- MiniTown：玩家行动造成可见世界变化；
- 概念 V1：俯视距离、海湾构图、冷蓝与暖橙关系。

### 动作

建立独立规则层、单一平面关卡数据、程序化 3D 资产、固定检查状态和真实浏览器试玩；不加入饥饿、制作、战斗、动物或多人系统。

### 产物与证据

- `tidewatch-game.html` 和实时 3D 场景；
- `TIDEWATCH_SLICE_CONTRACT.md` 与 `TIDEWATCH_SLICE_VALIDATION.md`；
- 8 项新规则检查、7 项旧规则检查全部通过；
- 桌面与 390×720 手机视口完成读潮、高潮浪击和点火验证。

### 失败与修正

- 本地预览阻止动态模块入口，改为预先打包运行脚本；
- 固定状态最初站得离火台太远，无法完成交互；
- 木材曾显示 `5 / 4`，说明内容状态与目标约束没有原子化；
- 产品验证了玩法结构，却没有复现四案例的美术资产质量，暴露“工作流借鉴”和“视觉生产借鉴”是两条不同链路。

### 技能候选

- `build-flat-tidal-risk-slice`：用单一平面、确定性潮位和双路线构建环境风险闭环。验证 `1 / 2`。
- `validate-web-game-checkpoints`：用固定状态、规则测试和真实浏览器路径验证可玩切片。验证 `1 / 2`。
- `visual-reference-to-runtime-asset-plan`：把案例视觉拆成角色、材质、灯光、动画和资产生产计划。当前仅识别问题，验证 `0 / 2`。

## Stage 03 · 试玩反馈

状态：等待用户完成一次真实试玩并只提供一个最大感受偏差。

本阶段要学习的不是“如何增加更多功能”，而是如何把“潮水没压力”“移动不舒服”或“回报不够强”翻译成一个有边界、可复现、有修改前后证据的检查点。

预期技能候选：`translate-player-feeling-to-checkpoint`。

## Stage 04 · 长期目标

状态：未解锁。必须先通过一次 Stage 03 修改前后对比。

要学习：哪些承诺应长期保存，Codex 如何从最新构建和历史证据继续，而不是重新解释项目。

预期技能候选：`maintain-evidence-backed-game-goal`。

## Stage 05 · 伴随与继续

状态：未解锁。

要学习：如何用 PLAY / NOW / NEXT / LOG / PROOF 让人不阅读代码也能知道当前版本、当前问题和下一步。

预期技能候选：`build-game-companion-control-plane`。

## 技能晋级规则

| 等级 | 定义 | 门槛 | 当前处理方式 |
| --- | --- | --- | --- |
| L0 · 观察 | 一次实践中发现的现象 | 有事实记录 | 写入阶段复盘 |
| L1 · 候选 | 一次样例中有效的方法 | 有产物、失败和运行证据 | 写入本台账 |
| L2 · 可复用方法 | 两个不同样例重复成功 | 输入输出契约稳定，失败边界清楚 | 形成独立方法文档和模板 |
| L3 · 正式 Skill | 能指导新任务并通过回归验证 | 脚本/模板/参考资料完整，至少两类任务通过 | 使用 Skill Creator 包装、测试和安装 |

当前所有沉淀最高处于 L1。没有任何方法可以因为一次《潮汐守望》实验就宣称为正式 Skill。

## 下一次研究的记录纪律

每完成一个产品检查点，必须在同一轮更新：

1. 游戏或网页产物；
2. 运行与试玩证据；
3. 本台账对应阶段；
4. 技能候选验证次数；
5. 失败边界和下一次复现条件。
