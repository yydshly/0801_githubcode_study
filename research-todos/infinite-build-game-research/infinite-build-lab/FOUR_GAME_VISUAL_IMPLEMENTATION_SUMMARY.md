# 四个参考游戏的视觉实现路线与 2D / 3D 差异

> Research 08 · 2026-08-06 研究结论
> 对应页面：[`capability-lab.html#visual-routes`](capability-lab.html#visual-routes)

## 一句话结论

四个游戏效果好，不是因为它们都用了更强的 3D 技术，也不是因为 2D 天然比 3D 好，而是因为它们选择了与镜头、玩法和资产条件相匹配的视觉路线。

在资源有限的情况下，2D 或 2.5D 可以把人物、服装、树叶、岩石、光影和动作细节预先画进图片，因此更容易快速获得完整、美观的第一印象。实时 3D 必须让模型从多个角度成立，还要同时解决几何、UV、材质、骨骼、动画、灯光、LOD 和性能，因此没有生产资产时很容易呈现为程序化卡通占位物。

## 四个游戏分别依赖什么

| 案例 | 主要视觉路线 | 效果成立的关键 | 优点 | 限制 |
| --- | --- | --- | --- | --- |
| Phantasy Codex Adventure | 2D Canvas + 像素背景 + 角色动作图集 + 实时 VFX/HUD | 人物、敌人、森林和动作帧已经画好；程序只负责切帧、碰撞、伤害和反馈同步 | 少量媒体即可获得明确角色身份和动作冲击力 | 镜头自由度低；新增动作、装备和方向通常需要继续绘制图片 |
| Phantasy Codex Online | DOM 界面 + 2D 角色/装备媒体 + 图标和状态面板 | 视觉重点是身份、装备、稀有度和成长，不要求完整可旋转世界 | 很适合背包、装备、属性和长期成长表达 | 不能据此证明开放世界、自由镜头或多人空间已经实现 |
| Backroom Center: Corrupted | 实时 3D + 模块化建筑 + 灯光、雾和后处理 | 走廊、墙体、设备等硬表面可以重复组合；压迫感主要来自尺度、重复、观察方式和光雾 | 用有限模块构造大空间，第一人称临场感强 | 高质量仍依赖模型库、材质和后处理；不适合直接推导真实人物和热带生态成本 |
| MiniTown | 等距风格化 3D + 固定镜头 + 重复建筑/植被 + 昼夜光照 | 固定等距视角降低了背面细节、动画和镜头适配要求；简化几何与风格一致 | 建造状态可以直接映射为可见世界变化，资产容易复用 | 不等同于写实开放世界；自由近距离观察会暴露模型和材质简化 |

## 为什么目标图片很好，而实时海滩仍偏卡通

目标图片是一张固定视角的生成图。它可以直接“画出”湿沙反光、真实人物、树叶密度、岩石裂缝、海浪泡沫、锈蚀船体、风暴云层和远景大气，却不需要提供这些对象的背面、碰撞、骨骼、动画或实时性能。

当前 `arrival-beach-visual-slice.html` 是实时 Three.js 场景，主要使用程序化几何：胶囊和球体组成的人物、简化叶片和灌木、单色岩石、基础船体和自定义海水着色器。它已经能够验证镜头、海岸纵深、人物比例、天气和空间路径，但没有生产级模型与纹理，因此视觉语言自然更接近风格化占位原型。

这两者回答的问题不同：

- 目标图片回答“最终可能想看到什么”。
- 视觉切片回答“这个空间、镜头和天气能否实时成立”。
- 生产资产阶段才回答“实时画面能否接近目标品质”。

## 2D / 2.5D 与实时 3D 的资源账

| 维度 | 2D / 2.5D 混合 | 完整实时 3D |
| --- | --- | --- |
| 细节来源 | 图片、动作图集、分层背景、透明特效、贴花 | 模型、UV、PBR 贴图、骨骼、动画、粒子、着色器 |
| 镜头 | 固定或半固定，通常只服务少量方向 | 自由旋转、远近变化，所有可见角度都要成立 |
| 人物 | 每个动作和方向是一组图片 | 一个可旋转模型配骨骼、蒙皮、动作和装备挂点 |
| 自然环境 | 远景和密集细节可直接画进图层 | 每棵树、岩石和地表都要考虑模型、材质、LOD 和实例化 |
| 状态变化 | 需要额外图片或图层，但实现直观 | 可以连续变化，但制作、渲染和优化链更复杂 |
| 早期视觉完成度 | 在固定镜头下较容易做高 | 没有生产资产时通常较低 |
| 长期自由度 | 受镜头和预制图片约束 | 可支持自由探索、动态光照和多角度交互 |

## 对当前海岛项目的推荐路线

当前最符合资源条件的路线是 2.5D 混合，而不是立即追求照片级自由 3D：

1. 使用 3D 地形、海岸线、碰撞、寻路、海水和天气保持真实空间与可玩性。
2. 使用半固定或受限制镜头，减少所有角度都必须达到同等质量的成本。
3. 使用 2D、预渲染或面向镜头的角色与植被素材提升人物身份、林缘密度、远景和天气细节。
4. 对近景关键物体逐类替换生产资产，而不是同时采购完整人物、生态和大地图资产库。
5. 玩法与视觉方向稳定后，再比较继续 Three.js、购买完整 3D 资产或迁移 Unreal 的真实成本。

推荐不等于已经决定。采用 2.5D、购买第三方资产或迁移 Unreal 都会改变后续生产路线，需要单独立项和明确授权。

## 已证明与未证明

### 已证明

- 2D 图片、角色图集和界面层可以用较低实时成本形成完整的动作与成长表达。
- 模块化实时 3D 很适合规则建筑、固定等距建造和光雾氛围。
- 海岛系统逻辑与视觉实现可以分开验证，不必等待照片级资产才开始测试玩法。

### 未证明

- 没有证明 2D 永远比 3D 好，或所有参考游戏都是 2D。
- 没有证明当前程序化海滩可以仅靠继续写代码自然达到目标图片质量。
- 没有证明 2.5D 能满足最终自由镜头、装备外观和近距离生态观察需求。
- 没有完成生产资产采购、授权核验、性能预算或 Unreal 技术验证。

## 下一次研究应做什么

如果继续当前方向，下一次只做一个可比较实验：在同一海滩镜头下，把“人物”或“近景植被”其中一类程序化占位物替换为 2D/预渲染资产，保留替换前后截图、交互和性能数据。这样才能实际判断 2.5D 是否比继续制作低配程序化 3D 更适合本项目。
